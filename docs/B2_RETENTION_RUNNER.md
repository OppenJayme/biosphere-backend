# Synthetic B2 retention runner

Prepared November 9, 2026. This implements the bounded experiment in the
[permission/retention checklist](./B2_PERMISSION_RETENTION_CHECKLIST.md).
It is prepared software with isolated test evidence, not a completed live B2
test or a production backup runner. Review and merge the
[owner-key setup dependency, #275](https://github.com/OppenJayme/biosphere-backend/pull/275)
before any live use. Obtain authorization for the specific live experiment first.

## What it does

The default command prints a plan without reading credentials, prompting,
creating files or contacting B2:

```powershell
pwsh.exe -NoLogo -NoProfile -File scripts/recovery/b2-retention-runner.ps1
```

An authorized run consumes the three scoped keys from #275, protected with
Windows DPAPI for the current user. It never reads `.env` or `backblaze.env`,
requests an administrative key, creates keys, changes bucket policy, sets Legal
Hold, bypasses Governance, hides versions, or touches existing objects.

The runner checks actual authorization restrictions for all three identities:
one exact bucket, one fresh `synthetic/retention-<run UUID>/` prefix, the expected
capabilities, distinct keys and bounded expiry. At least ten minutes must remain
of the six-hour key lifetime. It requires a private bucket, readable enabled
Object Lock, unset default retention and no lifecycle rules. Missing or unknown
metadata stops the run.

It generates one AES-256-GCM encrypted synthetic message, at most 1 KiB. The
decryption key stays in a local DPAPI receipt; it is not uploaded. The fixture
writer uploads only `probe.enc` in its assigned prefix, with Governance retention
ending 24 hours after the local intent timestamp. Compliance and every other
duration are rejected before prompts or credential access. These limits belong
to this trusted script; B2 key capabilities alone do not enforce them.

It validates the returned version's identity, length, SHA-1 and retention. It
then reads that immutable version and authenticates/decrypts its complete bytes:

1. Before either deletion check.
2. After the publisher's deletion attempt returns HTTP 401 `unauthorized`.
3. After the deletion-probe identity returns HTTP 401 `access_denied`.

Only those documented status/code pairs count. Token expiry, missing files,
timeouts, malformed errors, 403s and server failures stop the experiment.
Unexpected successful deletion also fails the test; only the new synthetic
object could have been affected. The runner never retries requests.

The [Native delete API](https://www.backblaze.com/apidocs/b2-delete-file-version),
[upload API](https://www.backblaze.com/apidocs/b2-upload-file),
[authorization response](https://www.backblaze.com/apidocs/b2-authorize-account)
and [bucket metadata](https://www.backblaze.com/apidocs/b2-list-buckets) define
these contracts. Live transport/permissions still need verification.

## Owner operation after review and authorization

Use a trusted, reviewed checkout with Windows PowerShell 5.1 or PowerShell 7 and
an absolute trusted Node.js 22+ executable. CI uses PowerShell 7; native 5.1
needs the local synthetic suite to pass on the operator's machine immediately
before use. Keep all owner material on a private, non-synced local filesystem.

The packet must exist under this checkout at
`.recovery-rehearsals/b2-owner-<run UUID>/test-keys.dpapi`, generated by #275 for
the same Windows user. Do not copy secrets into arguments or another checkout.
The run UUID and bucket name are references, not credentials.

```powershell
# Replace references locally; do not put a key in this command.
pwsh.exe -NoLogo -NoProfile -File scripts/recovery/b2-retention-runner.ps1 -Run -RunId '<owner setup UUID>' -BucketName '<exact test bucket>' -NodeExecutable '<absolute trusted node.exe>'
```

The prompt requires `LOCK ONE SYNTHETIC FILE FOR ONE DAY`. Declining leaves
everything untouched. Plan and successful verification exit 0; a stopped run
exits 1 with sanitized stage/counters. Argument-binding or host failures may
exit before structured output. `deploymentAuthorized` is always false.

## Receipts and uncertain outcomes

Before the upload request, an exclusive create reserves
`retention-attempt.dpapi`. It holds the exact object name, retention deadline,
decryption key and digest. Subsequent atomic replacements record the returned
file ID and successful verification. It contains no B2 application keys.
This file and the setup packet remain ignored private material.

Any existing attempt blocks a second run before provider access, including an
incomplete or unreadable attempt. Never delete it to force a retry. The process
may have committed the upload even if its response was lost. If intent exists
without a file ID, the owner must reconcile the exact prefix/name in the B2
console; the runner cannot infer absence from a timeout. Retained temporary
receipt files after a filesystem failure must also stay private.

Inspecting a receipt is local-only and exposes no key, object name or file ID:

```powershell
pwsh.exe -NoLogo -NoProfile -File scripts/recovery/b2-retention-runner.ps1 -Inspect -RunId '<owner setup UUID>'
```

`intent` means an upload may exist, `uploaded` means its response was verified,
and `verified` means both expected denials and all three readbacks completed.
Inspection does not contact B2 or refresh that evidence. Keep the encrypted
receipt until expiry/cleanup are reconciled. Cleanup and new credentials after
the six-hour keys expire are separate owner actions; there is no automatic
cleanup, scheduling, key revocation or retention change in this script.

## Isolated verification and limits

```powershell
# Windows native 5.1; no provider access or actual keys
node test/b2-retention-runner.test.cjs
# Windows CI, explicit preinstalled PowerShell 7
node test/b2-retention-runner.test.cjs --powershell7
```

The tests execute the real script, child encryption codec and Windows DPAPI in
owned temporary directories. Only prompts and external HTTP are simulated.
They cover plan/confirmation, unsafe modes/durations, scope/expiry, encrypted
version readback, wrong metadata/ciphertext, deletion errors and retained
unknown-outcome receipts. They do not prove provider behavior, fee guarantees,
expiry cleanup, anonymous access denial, hiding resistance or independent
custody. The roles cannot inspect Legal Hold; a live denial plus readable
Governance metadata is not proof that no administrator also placed a hold.

Transport redirects are disabled and each HTTP request has a 20-second timeout.
Only trusted Native API provider endpoints are accepted. At most 14 requests
are made on the successful path. Metadata parsing is size-checked after HTTP
receipt; PowerShell buffers responses, so this is not a streaming download cap.
The internal Node helper has no file/network access and receives secrets only
through captured pipes. Its synthetic format is not a production backup format.

November 9 local evidence: 24 checks passed with zero skipped using native
PowerShell 5.1 on both Node 22.14.0 and 24.7.0. The tests exposed and
corrected Windows null-string binding during atomic replacement, and a retry
report that incorrectly said no upload could exist. Scoped CJS lint, formatting,
PowerShell syntax, workflow YAML and diff checks passed. PowerShell 7 is not
installed locally; its Windows CI result must be checked on the pushed head.
No live B2 retention is established here.

Museum-source export, intended-source restore, institutional decisions,
continuing custody, production retention, runner deployment/scheduling and
BAK-002 remain open.
